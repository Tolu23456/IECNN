| 2026-11-01 (Phase 2) | In-training evaluation only scores a validation subsample (default 12,000 characters, config `training.eval_chars`), while every run's FINAL number always evaluates the FULL validation text. | 2026-11-01 (Phase 2) | bpc accounting kernel: characters are credited per *predicted token* as that token's expansion length (its decoded byte length). Over a full text this equals the text length exactly (decode(encode(x)) == normalize(x)), and it truncates correctly at a mid-window char cut, which a plain char count would not. | Spec file 07 section 7: "Count characters of the original text"; the expansion-length identity IS that count, guaranteed by the round-trip invariant. | Count chars only on full-window boundaries; rejected because truncated evaluation drifts from char boundaries. |
| 2026-11-01 (Phase 2, measured) | **PyTorch threads capped at 2 by default in training code** (config key `training.torch_threads`; 0 = auto). Reason: measured on the Actions runner (AMD EPYC 7763, 4 vCPU but only 2 physical cores): matmul 173 GFLOPS at 2 threads vs 138 at 4; grouped einsum 1.79 s vs 1.91 s. The 4th thread of SMT [hyper-threads, not real cores] steals cache from real cores. | The empirical benchmark; "use all processors" would have been slower on the very machines that run our experiments. | threads=4 (slower); threads=1 (needlessly half speed). |
| 2026-11-01 (Phase 2) | No bf16 on CPU: all training math stays float32. Spec file 06 suggests bf16 for matmuls with fp32 softmax — that guidance targets GPUs; EPYC 7763 has no BF16-free-speedup here and converting costs time. The fp32-softmax/log-space rule is kept (it is what we already do). | CPU benchmark reality; numerics identical. | Optional cpu-amp path; deferred until a GPU appears. |
| 2026-11-01 (Phase 3) | **Ring-neighbour distance for messages is cyclic**: `min(|i-j|, N-|i-j|)`, so dot 0's neighbours wrap around to dots 5 (N=6). Spec 05 says "ring" — a non-cyclic implementation would be a line, and the test `test_ring_wraps_correctly` pins the wrap behaviour (including N=1 = no neighbours). | The spec's topology table names it "Ring"; cyclic distance is what makes it one. | Linear distance (a "line" topology); rejected as not what the spec name means. |
| 2026-11-01 (Phase 3) | **Rung E0 sets `pooling: mixture` explicitly** and E1 sets `pooling: log_linear` explicitly (configs are not silently inherited). Rationale: E0 must be "exactly a plain uniform ensemble" — an arithmetic mean of dot distributions (mixture pooling with uniform weights), which is testable bit-exactly. E1 returns to the spec-default log-linear pooling. Config inheritance could have leaked E0's mixture into E1; both rungs now pin their own. | The test `test_e0_config_reproduces_uniform_ensemble_exactly` proves the E0 == plain-ensemble property; spec 08 defines E0 as that ensemble. | Inherit E0's pooling in E1; rejected because a rung's identity should not depend on another rung's config. |
| 2026-11-01 (Phase 3) | **Aux-loss lambdas come only from rung configs** (no silent defaults). E0: no aux losses. E1: lambda_d 0.1, lambda_k 0.05, lambda_w 0.05. lambda_r/lambda_c remain 0 until rungs introduce them (E2/E4). | Spec file 06 §2.7 gives defaults but "equal-compare the rungs" requires the *rung lists* to be explicit and reproducible from config alone. | Use spec §2.7 defaults everywhere; rejected — aux terms are part of what the ladder ablates. |
| 2026-11-01 (Phase 3) | **train.yml self-chaining chunks**: each seed is a matrix job running ≤320 min; ONLY exit code 124 (timeout cap) triggers an automatic self re-dispatch with `resume_artifact`; any other failure exits non-zero and fails loudly with no chaining, and artifacts always upload (stable name `{config}-seeds-{seed}{suffix}`, overwrite on upload).
